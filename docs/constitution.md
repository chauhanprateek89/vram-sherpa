# Constitution

Rules no plan, change or release may break. The architect checks each plan against them, the reviewer checks each diff, and release checks each PR. If a change needs to break a rule, the pipeline stops at a gate and names the rule's number. Only the user changes this file.

## Homelab rules

1. Deploy only to homelab-server, behind the existing cloudflared systemd tunnel. Never a second tunnel, a cloudflared sidecar, or a cloud host.
2. Free only. Any paid service, plan or usage-billed resource stops at a gate.
3. App ports bind to `127.0.0.1`. Databases are never published.
4. Delivery is pull-based: merge to main, CI, image to GHCR, smoke test, release; watchtower on the server pulls `:latest`. No inbound path to the server, no deploy keys, no self-hosted runners. The repos are public.
5. Only the app container auto-updates (watchtower label). Databases never do. Infrastructure images are pinned to a version.
6. Merging to main needs the user's sign-off, because merging deploys.
7. Secrets live in a `chmod 600` `.env` on the server, never in git.
8. In production, unknown `Host` headers are rejected, and the app honours `X-Forwarded-Proto` behind the tunnel.
9. HTML responses send a `Cache-Control` header, so a deploy shows on the next page load.
10. A UI change isn't done until QA has seen it in a real browser and compared it with the approved mockup.

## App-specific rules

11. The app is public and read-only. It has only GET routes, no accounts or auth, and nothing a visitor enters is ever stored. (`src/vramsherpa/main.py` `create_app`)
12. The database holds no user data. It is rebuilt from `data/seed_*.json` on every container start (`python -m vramsherpa.seed` runs before uvicorn), so a feature must never depend on database state that the seed files can't recreate.
13. The seed files are generated by `tools/ingest_catalog.py` from `tools/catalog_sources.yaml` and never edited by hand. All three share one `catalog_version`, and they must pass `tools/validate_catalog.py`, which CI enforces.
14. The catalog ships inside the image. Catalog changes reach production only through a merge to main and a release, never by writing to the live database, so a rollback restores the exact catalog that shipped.
15. Network calls to Hugging Face or any other outside service happen only in the offline catalog tooling and the `catalog-refresh.yml` workflow. The served app needs nothing but its Postgres at startup or at request time.
16. Every verdict shows the required VRAM, the available VRAM and the margin, not just a badge. `estimation.py`, the `/how-it-works` page and `ESTIMATION_POLICY_VERSION` change together.
17. There is no migration tool, only `create_all`, which never alters existing tables. Any change that adds or changes a column stops at a gate with an upgrade step for the persistent production volume.
18. A merge to main must pass `ci.yml` (ruff check, ruff format --check, catalog validation, pytest) and the release smoke test. Its checks may be added to but never removed or weakened: `/healthz`, the seed log line, the page render, https asset URLs and the 400 for an unknown Host.
19. Tests run without a real database (a temporary SQLite file per test) and without network access.
20. The production web command (seed, then `uvicorn … --proxy-headers --forwarded-allow-ips=*`) must stay identical in `docker-compose.prod.yml` and the smoke test in `release.yml`.
21. Any change to `static/css` or `static/js` bumps `ASSET_VERSION` in `src/vramsherpa/main.py`. That version is the only cache-busting for assets.
