# ADR-0006: The 390 px layout is built in templates and CSS only, with routes, fields and figures frozen

Date: 2026-10-25 · Revised: 2026-10-25 (Gate 2) · Status: accepted · Requirements: R-069, R-070, R-071, R-072, R-073, R-074, R-075, R-076, R-078

> **Revision, 2026-10-25 (Gate 2).** The first version rendered the filters closed and had an inline script open them before first paint at desktop width. Open at 1280 px, the filters push the first card's verdict past 1,100 px, beyond R-069's 800 px. At Gate 2 the user decided: "Filters start closed at both widths (not opened on desktop by script)" (`docs/decisions.md`). Point 4 below now says so, and no script opens the filters. The ADR's inline-script pattern now serves Top Picks instead, which the approved mockups show closed on a phone and open from 900 px (point 2). The same Gate 2 row allows states that show a message (ambiguous GPU, input errors) to end around 840 to 880 px at 1280 (measured 843 and 883 px); the 800 px target applies to the normal results view. Point 3 records where the mockups put the messages, and point 9 records two layout facts the build must respect, one of which (the results region moves out of the form) also stops the breakdown from pushing its URL into history.

## Context

The phone layout breaks today. Filters sit open between the form and the results. The answer comes after Top Picks and the filter chips. Model detail is a seven-column table in a horizontal scroll region, and formulas and long names can overflow. The overhaul must fix this at 390 px and 1280 px (Q-5) without changing any route, query parameter, fragment endpoint, figure or verdict (R-078), and it must keep working without JavaScript. Several requirements look like they need code: filters collapsed behind an active count (R-069: on phones at Gate 1, Q-3; at both widths since Gate 2), error and GPU messages shown once and refreshed with the results (R-071), a table with no horizontal scroll (R-074), and numeric keyboards (R-070). The form is not re-rendered on an in-place refresh: HTMX swaps only `#results-shell`.

## Decision

All layout work happens in Jinja templates, `styles.css` and small additions to `app.js`. `main.py` keeps every route, parameter and figure, and gains at most new template context values. Specifically:

1. **Frozen interface.** Route paths, query parameter names, form field `name`s, the HTMX attributes and targets (`#results-shell`, `hx-push-url`, `/results/why/…` with `hx-trigger="click once"`), and the ids and data attributes that `app.js` reads (`gpu_search`, `gpu_id`, `gpu-options`, `clear-gpu`, `vram_gb`, `theme-toggle`, `data-model-card`, `data-quant-btn`, `data-variant-pane`, `.chip-example`) do not change. Templates may be reordered and split into new includes (for example `results_top_picks.html`). `results_content.html` still composes the summary and the list, and the three `/results/partials/*` endpoints still return their templates.
2. **Answer first (R-069).** The result headline (the `N models fit or are tight` sentence, now the answer tile's heading, and the counts) moves to the top of the results region, in the answer tile (`#summary-banner`), with the active filter chips inside that tile. Top Picks follow the answer tile, as the approved mockups place them (Q-1): a `<details data-open-wide>` rendered closed, followed directly by an inline script that sets `open` when `matchMedia('(min-width: 900px)')` matches. So phones start with one collapsed row, wide screens start open when JavaScript runs, and without JavaScript the user can open it (R-078). The script sits inside `#results-shell`, and htmx 1.9.12 runs inline scripts in swapped content, so it also runs after each in-place refresh.
3. **Messages inside the swapped region (R-071).** The `role="alert"` error list and the `role="status"` GPU feedback are rendered only inside `#results-shell`, in the answer tile under the headline (as `final-results-errors` and `final-results-gpu-ambiguous` show), and removed from the form in `index.html`. Each response then shows exactly the current query's messages, once. Model detail keeps its own single error list.
4. **Filters disclosure (R-069, R-078; revised at Gate 2).** The filters stay in the one `<form>`, at the foot of the form tile, inside a native `<details>` rendered without `open` at every width, whose `<summary>` reads `Filters (N)` (`Filters (0)` with none). N is the number of active filter chips (R-031), rendered by the template from the chips the server already computes (`active_filter_chips|length`), so `main.py` does not change for it. No script opens the disclosure, at any width. The visitor opens it, with or without JavaScript, and the browser keeps it open until they close it or the page reloads. `app.js` updates N when a filter input changes, counting checked family, quantisation and `Recommended only` boxes and each non-empty, valid `Min params (B)` and `Max params (B)` value, which is what the server would turn into chips. The listener is delegated on `document`, so it survives an htmx history restore. The filters stay outside `#results-shell`, so an in-place refresh never closes them.
5. **Mobile-first CSS (R-070).** Base rules target 390 px and `min-width` queries add columns. `min-width: 0` on grid and flex children, `overflow-wrap: anywhere` on model names, GPU labels, source URLs and `code`, and no `white-space: nowrap` on text. Fields use 16 px text at phone width, and tap targets are at least 44 px. The header keeps its three items in one row, wrapping if needed. If they do not fit, a `<details>` menu is used, never a JavaScript-only menu.
6. **Numeric keyboards (R-070).** Number fields stay `type="number"` (so `min` and `step` are unchanged) and gain `inputmode="decimal"`.
7. **Model detail variants (R-074).** The `<table>` stays as the desktop markup. At phone width, CSS turns each row into a stacked block, with labels from `data-label` attributes on the cells. Explicit `role="table"`, `row`, `columnheader` and `cell` attributes keep the table semantics that some browsers drop when `display` changes. Provenance stays the last cell. `.table-scroll` is removed.
8. **Breakdown and how-it-works (R-073, R-075).** The breakdown becomes a definition list that wraps inside the card. Formulas wrap rather than scroll. The breakdown's placeholder becomes a distinct loading state, using htmx's `htmx-request` class on the `<summary>`, so no extra JavaScript is needed.

9. **Two layout facts from the approved mockups.** The mockups put `#results-shell` after the form rather than inside it, and the build must do the same. htmx 1.9.12 inherits `hx-push-url` from ancestors (`getClosestAttributeValue` in `determineHistoryUpdates`), so today each breakdown `<summary hx-get="/results/why/…">`, which sits inside the form, inherits the form's `hx-push-url="true"` and pushes `/results/why/<id>?…` into the address bar and history; a reload then shows the bare breakdown fragment (the R-081 defect in another form, found while planning). Outside the form the breakdown pushes nothing, with no `hx-*` attribute changed. `hx-target="#results-shell"`, the form's `hx-*` attributes and the `<noscript>` `Apply filters` button inside the form stay as they are, and htmx sends no form values with `GET` requests from elements inside a form, so nothing else depends on the shell being inside the form. The mockups mark the no-Top-Picks layout with a `no-picks` class on `<main>`, which sits outside `#results-shell` and is not re-rendered on an in-place refresh. The build keys that layout on markup inside `#results-shell` instead (for example a class on the shell's first child, or `:has()`), so it stays right after a refresh.

Layout is verified by QA in a real browser at 390 and 1280 px in both themes (rule 10). Pytest checks the markup invariants: frozen ids and attributes, each message rendered once, `inputmode`, `data-label`, and the R-078 reference queries returning the same models, order and figures.

## Alternatives considered

| Option | Why not |
| --- | --- |
| Render the filters twice (a phone drawer and a desktop sidebar) | Duplicate field names submit twice and break the URL contract of R-032. |
| Detect phones on the server (User-Agent) to decide `open` | Unreliable, and it varies the HTML by a header the cache layer does not key on (ADR-0004). |
| CSS-only disclosure (checkbox hack, `::details-content`) | The checkbox hack is poor for accessibility. `::details-content` styling is not yet in every target browser. |
| Server-rendered `open`, closed by script on phones | Phones without JavaScript would start with the filters open, against R-069. |
| Filters closed on phones and opened by an inline script at desktop width (the first version of this ADR) | Open at 1280 px they push the first card's verdict past 1,100 px, beyond R-069's 800 px. Rejected at Gate 2. |
| Filters in a full-width row or a sidebar beside the results | R-077 wants the tab order to match the screen, and the filters must stay outside the swapped `#results-shell`. At the foot of the form tile they satisfy both. |
| An out-of-band HTMX swap (`hx-swap-oob`) to refresh the in-form messages and filter count | Puts the same element in two templates and makes the full-page render emit stray oob markup. Moving the messages into the swapped region is simpler. |
| Replace the model detail table with cards at every width | A table is the right structure for comparing four variants side by side on desktop. Reflowing at phone width keeps both. |
| A JavaScript layout or component framework | No build step, and R-078 requires everything to work without JavaScript. |
| Automated visual regression in CI (Playwright screenshots) | New dev dependencies, browser downloads in CI and brittle baselines. Rule 10 already assigns this check to QA in a real browser. |

## Consequences

- `main.py` changes stay small, mainly the filter count and any wording context, so the R-078 figure checks are low risk.
- Everything that appears on scroll is pure CSS, so intermediate widths (for example 768 px) are not mocked or QA'd. The only guarantee there is no horizontal scroll.
- The inline Top Picks script joins the existing inline theme script. Both must survive if a Content-Security-Policy is ever added (none exists today).
- Every visitor, at every width and with or without JavaScript, sees the filters collapsed with the count, and opens them with one click or tap. Desktop visitors lose the open-by-default filters they have today; the count and the chips (R-031) show what is active without opening them.
- Top Picks are open by default only from 900 px and only with JavaScript. Without JavaScript they start collapsed at every width and can be opened (R-078).
- Moving the messages out of the form changes where they sit on screen. The approved mockups place them in the answer tile, under the headline.
