# ADR-0008: htmx history entries point at full-page URLs, and a cache miss reloads the page

Date: 2026-10-25 · Status: proposed · Requirements: R-081, R-032, R-078, R-080 · Amends: ADR-0004 (`Vary` value)

Revised 2026-10-25 (Plan): the breakdown `<summary hx-get="/results/why/…">` inherits the form's `hx-push-url="true"`, because htmx inherits that attribute from ancestors, so opening a breakdown pushes `/results/why/<id>?…` into history and the address bar. ADR-0006 point 9 moves `#results-shell` out of the form, which stops it with no `hx-*` change; a guard test keeps `#results-shell` outside `<form id="search-form">`.

Revised 2026-10-25 (Gate 2 round 1 redo): added fix 4, which redirects old `/results/partials/content` links opened as a normal page (not `summary` or `list`, per R-081) to `/results?<same query>` (the user's decision in `docs/decisions.md`). Re-wiring scripts after a cache hit is recorded as out of scope, because the user did not select it.

## Context

At Gate 2 round 1 the user decided to fix this bug in the overhaul: after a back navigation, the page can be replaced by the bare results fragment (R-081). The templates load htmx **1.9.12** from unpkg (`base.html`). The analysis below was checked against that version's `dist/htmx.js`.

- The form in `index.html` has `hx-get="/results/partials/content"`, `hx-target="#results-shell"` and `hx-push-url="true"`. With `"true"`, htmx pushes the response URL (`determineHistoryUpdates`: `responsePath || requestPath`). So the address bar and the history entry become **`/results/partials/content?…`**, not `/results?…`. ADR-0004's note said `/results?…`. That was wrong.
- Before each push, htmx saves the current `<body>` HTML to `localStorage` (`htmx-history-cache`, `historyCacheSize` 10). On popstate, `restoreHistory` swaps the cached body back in. On a miss (the entry fell out of the 10-entry cache, the storage was cleared, or the storage is unavailable), `loadHistoryFromServer` runs a GET on the entry's URL with `HX-Request: true` and `HX-History-Restore-Request: true`, and swaps the response into `<body>`.
- `results_partial_content` always returns `results_content.html`, and `results` returns it for any `HX-Request: true`. Either way the miss swaps a fragment into `<body>`, and the header, form and footer disappear.
- The same pushed URL also breaks reload and sharing: opening `/results/partials/content?…` directly returns the bare fragment, with no stylesheet. This contradicts R-032 ("a URL that reproduces the same results when opened directly"), and product raised it as Q-13.
- htmx 1.9.12 takes an `HX-Push-Url` response header in preference to the `hx-push-url` attribute. It has `htmx.config.refreshOnHistoryMiss` (default `false`), which makes a miss call `window.location.reload()` instead of an XHR. It reads config from `<meta name="htmx-config">` when it initialises.

## Decision

Four small changes, all inside the frozen interface of R-078 and ADR-0006: no route, parameter, `hx-*` attribute or target changes. Fixes 1 to 3 date from round 1. Fix 4 was added in the round 1 redo.

1. **Push the full-page URL.** `results_partial_content` sets the response header `HX-Push-Url: /results?<query>`, where `<query>` is the request's raw query string unchanged (`request.url.query`, already percent-encoded, with repeated `family` and `quant_bucket` kept in order). If the query is empty, the header is just `/results`. The form keeps `hx-push-url="true"`, and the header overrides it. Every history entry, the address bar and any copied link now name `/results?…`, which `results` renders as the full page for a normal request.
2. **Reload on a miss.** `base.html` gains `<meta name="htmx-config" content='{"refreshOnHistoryMiss":true}'>` in `<head>`, before the htmx script. A miss becomes a real browser load of `/results?…`, sent without `HX-Request`. The browser gets the whole document, the head scripts run, and `app.js` initialises on `DOMContentLoaded`, so the restored page works like a fresh one. A cache hit behaves as it does today.
3. **Server safety net.** `results` returns the fragment only when `HX-Request` is `true` **and** `HX-History-Restore-Request` is not `true`. Otherwise it returns `index.html`. This is the pattern the htmx documentation recommends for servers that branch on `HX-Request`. It covers the case where the meta tag is lost in a template rewrite. htmx 1.9.12 extracts `<body>` from a full-document response before swapping, so this path cannot nest a second header or footer. Because `/results` now varies on that header too, the ADR-0004 middleware sets `Vary: HX-Request, HX-History-Restore-Request` on HTML responses, in place of `Vary: HX-Request`.
4. **Redirect old partial links (revision, 2026-10-25).** Releases before this one pushed `/results/partials/content?…` into the address bar, so people have saved and shared links of that form. A browser opening one gets the bare, unstyled fragment.
   - **Telling the two apart.** `results_partial_content` checks `HX-Request` first. If it is exactly `true`, the request comes from htmx and is served exactly as today: the fragment, plus fix 1's `HX-Push-Url`. Anything else, including a missing header, is a normal page load. This is deliberately narrower than fix 3: R-081 requires every request carrying `HX-Request: true` to get the fragment, so the partial does not look at `HX-History-Restore-Request`.
   - **Response for a normal load:** `302 Found`, empty body, `Location: /results?<query>`. The `Location` is the same string as fix 1's `HX-Push-Url`: the raw `request.url.query` passed through unchanged (still percent-encoded, repeated `family` and `quant_bucket` kept in order), or just `/results` when the query is empty. One helper builds both strings. The `Location` is a relative URL with a fixed path. It is never built from the `Host` header or from `request.url`'s scheme and host. So it cannot point off-site, and the browser stays on whatever scheme it used (rule 8, `X-Forwarded-Proto`). Starlette's `RedirectResponse` defaults to 307, so pass 302 explicitly. Its URL quoting keeps `%`, `&`, `=` and `+`, so an encoded query passes through unchanged. If a test shows any re-encoding, set the header on a plain `Response` instead.
   - **Caching.** The redirect has no `text/html` body, so the ADR-0004 middleware, which keys on content type, skips it. The redirect therefore sets `Cache-Control: no-cache` and `Vary: HX-Request, HX-History-Restore-Request` itself. Both answers for the partial URL, the fragment and the redirect, then carry the same `Vary`, so a browser cannot replay the redirect for htmx's own request to the same URL, or the reverse. A 302 with no freshness information is not cached by default anyway.
   - **Host guard.** `host_guard` is HTTP middleware and runs before routing, so a request with an unknown `Host` gets the 400 JSON and never reaches the redirect (rule 8, and rule 18's smoke check is unchanged). The redirect sits in the handler, not in a new middleware, so there is no middleware order to get wrong.
   - **Placement.** The check is the first statement in the handler, before `_results_page_context`, so a redirect makes no database query. FastAPI validates the query parameters before the handler runs. So a malformed value such as `context_tokens=abc` returns the same 422 JSON that `/results?context_tokens=abc` returns, without a redirect. The visitor sees the same outcome, only the address differs.
   - **`summary` and `list` are not redirected** (R-081). Their handlers are unchanged. They have had no caller in the templates since they were added (72318d6), and no release ever pushed them into history, so nobody got them in the address bar from the app.
   - **Old history entries.** A pre-release history entry naming `/results/partials/content?…` that misses the cache reloads under fix 2 as a normal load. It gets the 302, the full page loads at `/results?…`, and the address bar updates. If the fix 2 meta tag were ever lost, htmx's restore request carries `HX-Request: true`, so it gets the fragment, as it does today. That needs both a lost tag and a pre-release entry, and the fix 2 guard test catches the lost tag.

Guards (pytest, rule 19):

- `GET /results/partials/content?vram_gb=24&context_tokens=4096&family=a&family=b` with `HX-Request: true` carries `HX-Push-Url: /results?vram_gb=24&context_tokens=4096&family=a&family=b`.
- `GET /results?…` with both `HX-Request: true` and `HX-History-Restore-Request: true` returns the full page (the header, form and footer markers). With only `HX-Request: true`, it still returns the fragment (R-032).
- The rendered `base.html` contains the `htmx-config` meta tag with `refreshOnHistoryMiss` set to `true`, before the htmx `<script>`.
- HTML responses carry both names in `Vary`.
- Fix 4 (use `follow_redirects=False`, since the test client follows redirects by default): `GET /results/partials/content?vram_gb=24&context_tokens=4096&family=a&family=b` without `HX-Request` returns 302 with `Location: /results?vram_gb=24&context_tokens=4096&family=a&family=b`, `Cache-Control: no-cache`, both names in `Vary`, and no body. The same holds with `HX-Request: false`. With no query, `Location` is `/results`.
- Fix 4: the three partials with `HX-Request: true` still return 200 with the fragment and no `Location`, as the existing tests check. `/results/partials/summary` and `/results/partials/list` without `HX-Request` also still return 200 with their fragments.
- Fix 4: with `allowed_hosts` not `*`, `GET /results/partials/content?vram_gb=24` without `HX-Request` and with an unknown `Host` returns the 400 JSON with no `Location`.

R-081's browser steps (forcing a miss by clearing `htmx-history-cache`, and making 12 refreshes against the 10-entry cache) are QA's check in a real browser (rule 10).

## Alternatives considered

| Option | Why not |
| --- | --- |
| Only the server branch (`HX-History-Restore-Request` returns the full page), with the URL left at `/results/partials/content` | Means changing the partial endpoint as well, still leaves reload and shared links broken, and `loadHistoryFromServer` swaps a new `<body>` without rerunning `app.js`'s `DOMContentLoaded` setup, so the theme toggle and GPU input wiring would be dead on the restored page. |
| Only `refreshOnHistoryMiss`, with the URL unchanged | The reload fetches `/results/partials/content?…` without `HX-Request`, and that endpoint returns the fragment anyway. The bug moves rather than going away. |
| Change the form to `hx-get="/results"` | Fixes the pushed URL with no header, but changes an `hx-*` attribute that ADR-0006 and R-078 freeze, and leaves `/results/partials/content` with no caller. The response header gets the same effect with no template change. |
| `historyCacheSize: 0` or `hx-history="false"` (always fetch from the server) | Turns every Back into a server round trip, and still needs fix 1 or fix 3 to avoid fragments. |
| Make the partial render the full page for non-htmx requests, instead of fix 4's redirect | The partial would need to render `index.html` as well, and the address bar would keep the old form, so a link re-shared from it stays old forever. The redirect retires the old form after one visit and keeps one full-page route. |
| Fix 4 as a new middleware on the partial's path | It would run before parameter validation, but Starlette runs the middleware registered last outermost. Registered after `host_guard`, it would redirect before the host check. Putting the redirect in the handlers makes the order structural. |
| Fix 4 with 301 or 308 (permanent) | Browsers cache permanent redirects for a long time, so one would outlive a rollback or a later change. A cache that ignored `Vary` could also replay it on htmx's own request to the same URL. A 302 with `no-cache` takes effect, and stops, at once. 303 and 307 behave like 302 for a GET. 302 is the most widely understood. |
| Upgrade htmx to 2.x | Out of scope for a restyle, changes extension and attribute behaviour, and 2.x has the same miss path. Not needed for this fix. |

## Consequences

- A Back or Forward that misses the cache always shows the full page, with working scripts (R-081). A cache hit is unchanged.
- As a side effect, reload and copy-and-paste of the address bar after an in-place refresh show the full page (Q-13). Fixing back navigation requires this: the history entry and the address bar are the same URL.
- Links and history entries created before the release name `/results/partials/content?…`. Opened as a page, they now redirect to `/results?…` and show the full page (fix 4). The address bar then shows the new form, so a link re-shared from it is the new form.
- `/results/partials/content` now answers a non-htmx request with a 302 instead of a fragment. htmx requests from the form are unchanged, and so are `summary` and `list`. The app itself never sends a non-htmx request to the partial, so R-078's frozen interface holds for everything the app sends.
- A malformed old link (for example `context_tokens=abc`) still gets FastAPI's 422 JSON rather than a redirect, exactly as the same query on `/results` does.
- A miss now costs one full page load instead of one fragment request. With a 10-entry cache this is rare.
- **Out of scope (the user did not select it at Gate 2 round 1 redo, 2026-10-25):** re-wiring the theme toggle and the GPU input after htmx restores a page from its cache. On a cache **hit**, htmx swaps `<body>` from `localStorage`, so listeners that `app.js` attached to individual elements (`theme-toggle`, `gpu_search`, `vram_gb`, `clear-gpu`, `.chip-example`) are lost on the restored page. Event delegation on `document` survives, which is why the quantisation selector keeps working. This ADR does not change that, and it stays a known issue outside this change. Rerunning the init functions on `htmx:historyRestore` would fix it if it is ever taken up. A cache **miss** is not affected, because fix 2 reloads the page and `app.js` initialises normally.
- If htmx is ever upgraded or its pin changes, the guards above must be rechecked against the new version's history code.
- `UI: no` (R-081). No visual change and no mockup.
