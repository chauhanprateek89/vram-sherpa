Earlier history: 2026-10-25, as built at main 96572b1 (v0.1.48) with the overhaul proposed; revised 2026-10-25 after Gate 2 round 1 (ADR-0007 revised, ADR-0008 added, rule 21 amended), and again after the round 1 redo (ADR-0008 revised: old `/results/partials/content` links redirect to `/results`), and after Gate 2 (ADR-0005 accepted: the styled GPU list is built; ADR-0006 revised: filters closed at both widths, results region outside the form). ## Purpose

VRAM Sherpa is a public, read-only web app. You pick a GPU or type in a VRAM amount and a context length (**proposed, R-083:** on `/` one centred box takes a GPU or a VRAM number such as `12 GB`, and the results, with the context and filters, live at `/results`), and it estimates which local LLM model variants (quantisations) will fit, using a published formula (Estimation Policy v0.1) and showing the numbers behind each verdict. (**Proposed, R-084:** `/results` opens on a gist of counts and Top Picks; the models come one verdict and one page at a time.) It is for people choosing which open-weight model to run on their own hardware. It has no accounts and stores nothing that users enter.

## Data

- **Store:** PostgreSQL 16 in a container with the named volume `pgdata` (in both the local and the prod compose files). Tests use a temporary SQLite file per test (`tests/conftest.py`). CI starts a Postgres service and sets `TEST_DATABASE_URL`, but no code reads that variable.
- **Tables** (`src/vramsherpa/models.py`): `gpus` (id text PK, vendor, name, vram_gb, notes), `models` (id, name, family, params_b, model_type, license, gated, kv_gb_per_1k_ctx, sources as a JSON string), `variants` (id, model_id FK with cascade, quant_bucket, quant_label, bits_effective, notes, sources, recommended), `catalog_meta` (key/value, currently only `catalog_version`).
- **Seed data:** `data/seed_gpus.json`, `data/seed_models.json` and `data/seed_variants.json`, each shaped `{"catalog_version": "YYYY-MM-DD", "items": [...]}`. Current catalog: 2026-10-23, with 35 GPUs, 95 models and 380 variants. The files are generated by `tools/ingest_catalog.py` and committed. They are also copied into the image (`Dockerfile`), so every release carries its own catalog.
- **Persisted versus rebuilt:** the database holds no user data. It is rebuilt from the seed files every time the container starts. Seeding only upserts: rows that were dropped from the seed files stay in an existing volume until it is recreated.
- **Schema changes:** there are no migrations. `create_all` will not add columns to existing tables, so a new column breaks seeding on an old volume (`UndefinedColumn`). The fix is `docker compose down -v` or a manual `ALTER TABLE` (README, "Upgrading an existing database"). This happened when onboarding re-ran the local stack: the local volume had no `models.gated`.
- **Discovered models** live only in `data/seed_models.json` (flag `discovered: true`). `_load_discovered_models` reads them back on every ingest, so a refresh adds to the catalog and never drops earlier finds.

## Key flows

1. **Estimate request.** The browser sends `GET /results?vram_gb=…|gpu_id=…|gpu_search=…&context_tokens=…&family=…&quant_bucket=…`. `host_guard` checks the Host header. `results` calls `_results_page_context`, and `_resolve_available_vram` turns the GPU id, the search text (including VRAM hints such as "24GB") or the manual number into an available VRAM figure. **Proposed (ADR-0011):** before that, a `gpu_search` that is a box number (`12`, `12 GB`) with no `gpu_id` or `vram_gb` is rewritten to `vram_gb`, so the page is the `/results?vram_gb=<n>` page; and **(ADR-0010)** a page load with no hardware at all is redirected to `/` first. `_build_results` queries variants joined to models with the filters applied, and `estimate_variant` scores each row. `_group_results_by_model` builds the cards, and the templates render `index.html`, or only `results_content.html` when the request comes from HTMX. **Proposed (R-084, ADR-0014, ADR-0015):** the same steps run for every view, and the view picks what reaches the template: no cards for the gist, or one verdict's sorted page. See flows 11 to 14.
2. **HTMX interaction.** The form in `index.html` sends `hx-get` requests to `/results/partials/content`, which swaps `#results-shell`. The "why" buttons in `results_list.html` fetch `/results/why/{variant_id}` and show the formula breakdown from `estimate_breakdown`. As built, `hx-push-url="true"` pushes the response URL, so the address bar and history entry become `/results/partials/content?…`. Reloading that URL, or missing htmx's 10-entry `localStorage` history cache on Back, returns the bare fragment (R-081).
3. **Container start.** The compose command runs `python -m vramsherpa.seed` (which creates tables and seeds, printing `Seeded catalog_version=…`) and then uvicorn with `vramsherpa.main:create_app --factory`. If seeding fails, the container exits. `/healthz` returns 503 until the catalog rows exist.
4. **Catalog refresh.** The weekly workflow runs `ingest_catalog.py`: it loads the curated YAML, carries over earlier discoveries, discovers new models from the tracked HF orgs (min 50k downloads, at most 20 per org, exclusion patterns, `params_b_overrides`), generates variants and writes the seed files. It then runs `validate_catalog.py` and opens a "Catalog refresh YYYY-MM-DD" PR. Merging that PR is an ordinary merge to main, so it releases and deploys.
5. **Release and deploy.** A merge to main triggers `release.yml`: CI, then the version (`v<pyproject major.minor>.<git rev-list --count HEAD>`), fail if the tag exists, build and push the image to GHCR under `sha-…` only, and smoke-test that digest against Postgres. The smoke test checks that /healthz answers, that the seed log line appears, that `/` renders (**proposed, ADR-0013:** and that `/results?vram_gb=24&context_tokens=4096` renders the summary for `Manual VRAM (24 GB)` with status 200), that asset URLs are https behind `X-Forwarded-Proto: https`, and that an unknown Host gets 400. Only then does it tag that same digest `vX.Y.N` and `latest` (`docker buildx imagetools create`, no rebuild), and then push the git tag and create the GitHub Release. On the homelab, watchtower sees the new `:latest` within 5 minutes and recreates `web`; it only ever sees a `latest` that passed the smoke test. **Proposed (ADR-0019):** the smoke test also requests `…&verdict=fits` and requires exactly 200 with `data-model-card`.
6. **Filters and messages (proposed, ADR-0006, revised at Gate 2).** `index.html` renders the filters in a `<details>` without `open`, at both widths, whose summary shows `Filters (N)`, with N the number of active filter chips. No script opens it. Changing a filter fires the same `hx-get` to `/results/partials/content` as today. `app.js` updates N, and the swapped `#results-shell` now carries the error and GPU-search messages, so stale messages disappear with the old results.
7. **How it works (proposed, ADR-0007, revised 2026-10-25).** `how_it_works` loads the curated model named in R-075 (`WORKED_EXAMPLE_MODEL_ID`) with `session.get(Model, …)` and picks its `Q4` variant. It calls `estimate_breakdown` with that row's params_b, bits_effective and kv_gb_per_1k_ctx at 2048 tokens, which is the same call `/results/why/{id}` makes for that card (4.95 + 0.98 + 1.40 = 7.33 GB with catalog 2026-10-23). The page renders the model name, the inputs and the four steps beside the unchanged formulas. If the model or its Q4 variant is absent, or the catalog is unseeded, it computes the same steps from the declared fallback inputs (8, 4.5, 0.48, 2048) and labels them "an 8B model at Q4", with no name (open as Q-12). It always returns 200. `ESTIMATION_POLICY_VERSION` stays v0.1.
8. **Back and forward (proposed, ADR-0008).** An in-place refresh calls `/results/partials/content`, whose `HX-Push-Url` header makes htmx push `/results?…`. On Back or Forward, htmx restores the body from its `localStorage` cache. On a miss, `refreshOnHistoryMiss` reloads `/results?…` as a normal request, which returns the full page and reruns `app.js`. **Proposed (ADR-0017):** `historyCacheSize` becomes 0, so nothing is cached and every Back and Forward takes the miss path. If the meta tag is ever missing, htmx's restore request carries `HX-History-Restore-Request: true`, and `results` answers it with the full page too. Links and history entries from before the release name `/results/partials/content?…`. Opened as a page, or reloaded on a miss, they get a 302 to `/results?<same query>` and show the full page with the new address. `host_guard` still runs first, so an unknown `Host` gets the 400 before any redirect.
9. **Landing to results (proposed, R-083, ADR-0009 to ADR-0012).** `GET /` renders `landing.html`: the box (`#gpu_search`, autofocused, inside `#landing-form`, a plain `GET /results` form with no `hx-*`), the chips as links and the submit control. Typing and pressing Enter or `Check compatibility` navigates to `/results?gpu_search=<text>`; choosing a styled suggestion writes the exact label and submits the same form; a chip is a link to `/results?gpu_id=…` or `/results?vram_gb=…`, each with `context_tokens=2048`. `/results` applies the GPU-or-number rule and renders the results page at 2k with no filters. A blank box is stopped by a submit handler with JavaScript, or redirected back to `/` without it. `Clear` (now a link), the logo and `Estimator` load `/`. Back from `/results` to `/` is a normal document traversal, not an htmx restore.
10. **Results without hardware (proposed, ADR-0010).** A page load of `/results` with `gpu_id`, `gpu_search` and `vram_gb` all absent or blank gets `302 Location: /` with `Cache-Control: no-cache` and the `Vary` header, before any database query. htmx requests (`HX-Request: true`, including history restores) and requests with unusable hardware (`vram_gb=abc`, `gpu_id=no_such_gpu`) keep the 8 GB page. An old `/results/partials/content` link with no hardware takes two relative hops: to `/results` (ADR-0008) and then to `/`.
11. **Gist (proposed, R-084, ADR-0014, ADR-0015).** `GET /results?vram_gb=24&context_tokens=4096`. `_results_page_context` computes every model as today, makes one card per model and tallies the counts. With no valid verdict it passes no cards to the template. The response holds the answer tile, the three controls as links, the note and Top Picks open.
12. **Select a verdict in place (proposed, R-085, R-087, R-090, ADR-0018).** The user clicks `Fits`. The body listener sets `aria-busy` and `Loading models`. htmx requests `/results/partials/content?<query>&verdict=fits` and swaps `#results-shell`. The response's `HX-Push-Url` pushes `/results?<query>&verdict=fits` as one history entry. Focus moves to `#list-heading`, which scrolls into view. A page or size link does the same. Selecting `Fits` again requests the query without the three parameters and keeps focus on the control. On a network failure or a status of 400 or above, nothing swaps or pushes, and `#results-error` shows the message.
13. **Change a filter inside a list (proposed, R-089, ADR-0016).** A filter change fires the form's `hx-get`. On `htmx:configRequest`, because the trigger is not `submit`, `app.js` adds `verdict` and `page_size` from `#summary-banner`; the form has no `page`. The response shows page 1, or the gist with R-085's message if the count fell to 0, keeping `data-verdict` so a later change can restore the list. `Check compatibility` or Enter is a `submit`, so it adds nothing and lands on the gist. Without JavaScript, `Apply filters` sends `apply_view=<verdict>:<size>`, and `results` answers 302 to the address with the real parameters.
14. **Back, Forward and reload with a view (proposed, R-088, ADR-0017).** After `Fits`, page 2, Back: htmx finds no cache and reloads `/results?…&verdict=fits`, a full page from the server with the form rendered from the address. Back again gives the gist; Forward walks them in turn. Filter changes after that read `data-verdict` from the page on screen, so they apply to the view shown.

## UI/UX overhaul (proposed)

- **Scope.** Every screen and state in R-067, at 390 and 1280 px in both themes, restyled in the single direction the user picks at Gate 2 (R-068). The HLD fixes the mechanism, not the look: tokens and component classes (ADR-0001), font delivery (ADR-0002), the mark and favicon (ADR-0003), and the layout techniques (ADR-0006).
- **Requirements that touch the UI:** R-067 to R-078 (all `UI: yes`). R-079 (asset version), R-080 (`Cache-Control`) and R-081 (back and forward restore the full page) are `UI: no` but ship with them.
- **Frozen interface (R-078).** Routes, query parameters, form field names, the three `/results/partials/*` and `/results/why/{id}` endpoints, the HTMX targets, and the ids and data attributes `app.js` reads are unchanged. So are the estimation code, the figures and the verdicts. `main.py` gains only the HTML cache middleware, the filter count, the worked-example lookup and context, the `HX-Push-Url` header on `/results/partials/content`, the `HX-History-Restore-Request` check in `results`, and the 302 from `/results/partials/content` for non-htmx requests (which the app itself never sends). The `hx-*` attributes are unchanged. The response header overrides `hx-push-url="true"`.
- **No new runtime pieces.** No new service, route, dependency, build step or paid resource. New files are templates, CSS and JS edits, and static fonts and images.
- **Packaging trap.** The image installs the package non-editably, so new `static/fonts/` and `static/img/` files must be added to `[tool.setuptools.package-data]` in `pyproject.toml`, or production serves 404 while tests pass. A pytest checks the globs, and the release smoke test fetches every `/static/` URL on `/` (ADR-0002).
- **Cache-busting.** Rule 21 was amended at Gate 2 (2026-10-25): each task that changes anything under `src/vramsherpa/static/` (CSS, JS, fonts, images, favicons) bumps `ASSET_VERSION` (R-079). Font files also keep versioned names, because `styles.css` loads them by a plain `url()` (ADR-0002).

### The view

`parse_results_view(request.query_params)` gives `ResultsView(verdict, page, page_size)`, and `_results_page_context` reads it, so all four routes behave alike and no value can produce a 422 (ADR-0014). The three parameters are not declared on the handlers.

| Parameter | Valid | Anything else | Note |
| --- | --- | --- | --- |
| `verdict` | exactly `fits`, `tight`, `wont-fit`; the last value if repeated | no verdict: the gist | `FITS`, `green`, empty and `%3Cscript%3E` are never written back |
| `page_size` | exactly `5` or `10` | 5 | ignored with no valid verdict |
| `page` | whole ASCII digits, 1 or more | 1 | above the last page shows the last page, with no redirect; ignored with no valid verdict |

What a request shows, on the full page and in every partial alike:

| Query | Selected | Controls | List area | Top Picks | Note under the controls |
| --- | --- | --- | --- | --- | --- |
| no valid verdict, some count above 0 | none | links, inert at 0 | nothing, or the empty state when `Fits` and `Tight` are both 0 | open | `Choose Fits, Tight or Won't fit to see the models.` |
| no valid verdict, all counts 0, seeded | none | all inert | the empty state | hidden (R-024) | none |
| valid verdict, its count 0 | none | as the gist | as the gist | open | as the gist, plus `No models in <verdict> with these settings.` in `role="status"`; `verdict` stays in the address (R-089) |
| valid verdict, its count above 0 | that verdict | selected link marked `aria-current="true"` | heading, sizes when the count is above 5, cards, page controls when there is more than one page | closed, opened from 900 px by the existing script | `Pick a quantisation on any card to see how it changes.` |
| unseeded | none | all inert | R-026's two sentences | hidden | none |

An unseeded request naming a verdict gets R-085's message as well as R-026's sentences, because R-085's rule has no exception. R-067's G11 does not name a verdict.

### Partial routes and agreement

| Route | Template | Holds |
| --- | --- | --- |
| `/results` page load | `index.html`, which includes `results_content.html` | the form and everything below |
| `/results` with `HX-Request: true`, `/results/partials/content` | `results_content.html` | summary and list; the partial also sends `HX-Push-Url: /results?<same query>` |
| `/results/partials/summary` | `results_summary.html` | answer tile, Top Picks, selected control marked; no card |
| `/results/partials/list` | `results_list.html` | the selected page of cards, or no card |

One context function and one set of includes means the full page and the partials cannot disagree. A pytest holds this: for G1 to G8, the body of `/results/partials/content?<q>` with `HX-Request: true` appears exactly inside the body of `/results?<q>` (ADR-0014 point 7).

### Address, history and bad values

- **Links.** `view_query` builds each control's query from the raw request query, so `family`, `quant_bucket` and unusable hardware such as `vram_gb=abc` travel unchanged (R-088). `page` is left out at 1, `page_size` at 5. Selecting the selected verdict drops all three.
- **Pushing.** The partial's existing `HX-Push-Url` pushes one entry whose path is `/results`, so the address always reproduces the view on reload or in a private window (R-081, R-088).
- **Back and Forward (ADR-0017, amends ADR-0008).** htmx's `localStorage` snapshot holds the view, and R-088 forbids that, so `historyCacheSize` becomes 0. Every Back and Forward takes the existing `refreshOnHistoryMiss` path: a full page load of the entry's address. That also gives R-086's default variant on return, and removes ADR-0008's dead-listener issue. Back from `/models/<id>` is ordinary document history to the same address.
- **Old links.** No `verdict` means the gist, with `page` and `page_size` ignored. `/results/partials/content` opened as a page still redirects with its raw query, so it keeps the view (R-081). `/results?verdict=fits` with no hardware and no `HX-Request: true` still redirects to `/` first (R-013, ADR-0010).

### Lists, counts and filters (ADR-0015)

- All models after filters become cards; `_default_variant` applies R-016, including the new no-usable-variant branch. Counts tally the cards, so each count equals its list's total. The headline's N is `Fits + Tight`.
- `Fits` and `Tight` sort by `(-params_b, model_name, model_id)`. `Won't fit` sorts by `(required_vram_gb - available_vram_gb, -params_b, model_name, model_id)`, unrounded, closest to fitting first. `model_id` only breaks a tie between two identical names, which does not occur in the current catalog. It keeps each page stable. This key reproduces every worked example in R-086 against catalog `2026-10-23`.
- Filters and context apply in `_variant_query`, before anything is counted (R-089). Verdict, page and size are not filters, so they add no chip and do not change `Filters (N)`, which counts form controls and chips only.
- `paginate` clamps, then only the slice goes to the template. Each page is a server round trip of the same size of computation as today's filter change, and carries 5 or 10 cards where the reference query's response today carries 71 in 752 KB.

### Form actions (ADR-0016)

| Action | With JavaScript | Without JavaScript | Result |
| --- | --- | --- | --- |
| Verdict, page or size control | `hx-get` to the partial | plain link | that view |
| Context preset, family, quantisation, `Recommended only`, min and max params | `htmx:configRequest` adds `data-verdict` and `data-page-size` from `#summary-banner` | no auto-submit, as today | same verdict and size, page 1 |
| `Apply filters` | not rendered (`<noscript>`) | `name="apply_view" value="<verdict>:<size>"`, then 302 to the real parameters | same verdict and size, page 1 |
| Chip, `Try Q4`, `Lower context` | plain link | plain link | same verdict and size, page 1 (full load, so the form follows) |
| `Check compatibility`, Enter | `configRequest` adds nothing for a `submit` event | button has no name and is the form's default | the gist, none of the three in the address |
| `Clear` | link to `/` | link to `/` | landing page |

### In-place loading and accessibility (ADR-0018)

- Each control is an `<a>` with `href="/results?<q>"` and `hx-get="/results/partials/content?<q>"`, from one macro, so without JavaScript each is a full page of the same view (R-090). The links and the form share `hx-sync="#results-shell:replace"`, so the latest action wins.
- Inert states are `<span>`s, out of the tab order. The current page is a `<span aria-current="page">`; the current size and the selected verdict stay links, marked `aria-current="true"`. Page controls sit in `<nav aria-label="Pages">`, with `aria-label="Page <n>"` on numbers and `aria-hidden` on `…`. Verdict controls sit in a `role="group"` named `Show models by verdict`, and sizes in one named `Models per page`.
- `#results-feedback`, outside the swap, holds a `role="status"` paragraph for `Loading models` and a `role="alert"` paragraph for `Could not load the models. Try again.`. Listeners on `document.body`, filtered to requests targeting `#results-shell`, drive these and `aria-busy`. Breakdown requests are not affected. Without JavaScript, both stay empty.
- After a verdict, page or size load, focus moves to `<h2 id="list-heading" tabindex="-1">`, whose text is the announcement, and the heading scrolls into view, without animation under reduced motion. After a collapse, focus returns to the control. Form-driven refreshes leave focus in the form. Failures and aborted requests move nothing.
- `syncBoxVram` and `syncVramInvalid` skip responses to these links, so typed text stays (R-090).
- Ctrl, Cmd or Shift click opens a new tab: a capture-phase listener keeps htmx from cancelling it.

### Gist and Top Picks figures

- **No estimation change.** `estimation.py`, `/how-it-works` and `ESTIMATION_POLICY_VERSION` (`v0.1`) do not change, so there is no version bump (R-086, rule 16). Everything shown is a value `estimate_variant` already returns.
- **Top Picks.** `_top_picks` keeps its rows and rules (R-024). `results_top_picks.html` adds, from the same `ResultRow` the card's pane uses, the `verdict` macro, `'%.2f'` `GB needed`, `'%.1f'` `GB` and `'%.1f'` `GB spare`, so a pick's figures equal that variant's pane by construction (R-092). A pick is always usable, so `GB over` cannot occur. No gauge, no breakdown.
- **Counts.** They are tallies of models, not verdicts on a model, so they carry no figures (Q-39, rule 16). Every model in a list shows all three figures through its card (R-086).
- **Top Picks open or closed.** The gist renders `<details open>`, with or without JavaScript. With a verdict selected it renders as today, closed with `data-open-wide` and the inline script (R-084, R-085). Top Picks read all rows, not the slice, so they stay the same across verdicts and pages (Q-40).

### Release and assets

- **Smoke test (ADR-0019).** One added check: `…&verdict=fits` must answer exactly 200 with `data-model-card`. Every other check stays, including ADR-0013's (rule 18). The web command is untouched (rule 20). `test_r082_release_order.py` adds the needles.

- **`Cache-Control` (R-080).** The middleware keys on content type, so all new HTML is covered. The `apply_view` redirect has no HTML body and sets `Cache-Control` and `Vary` itself.

### What the mockups need (G1 to G13)

The tools need `pyyaml`, which arrives through `pre-commit` in the dev extras.
- **Production:** the homelab runs `docker-compose.prod.yml` with a `chmod 600` `.env` (`APP_ENV`, `ALLOWED_HOSTS`, `PUBLIC_HOSTNAME`, `POSTGRES_PASSWORD`, optional `IMAGE_TAG` for rollback). The existing cloudflared systemd tunnel reaches `127.0.0.1:8000`. CI has no inbound path to the server. The GHCR package must be public.
- **Settings that matter:** `ALLOWED_HOSTS` is the only control on accepted hosts. `APP_ENV` only changes the startup error message, and the code never reads `PUBLIC_HOSTNAME`. So the public DNS name must be in `ALLOWED_HOSTS`, or the host guard rejects tunnel traffic with 400. `docs/RELEASE_AND_DEPLOY.md` says otherwise. `--proxy-headers --forwarded-allow-ips=*` must stay on the prod command, or asset URLs fall back to http:// and the browser blocks them as mixed content.
- **Caching:** HTML responses send no `Cache-Control` header (checked on `GET /`). Static assets are cache-busted by the hand-bumped `ASSET_VERSION` (`20261024a`). **Proposed (ADR-0004):** every HTML response, fragments included, sends `Cache-Control: no-cache` and `Vary: HX-Request, HX-History-Restore-Request`, so the next load after a deploy gets new HTML naming the new `ASSET_VERSION`. `/static` caching is unchanged, and the smoke test checks the header on `/`.
- **Version visible on the live site:** there is no release version in any response. The marker closest to it is `styles.css?v=<ASSET_VERSION>` in the HTML, which changes only when a developer bumps it. `/healthz` and the footer show `catalog_version`, which changes only when the catalog does. The release tag exists only as the image label `org.opencontainers.image.version`.
- **Live URL:** unknown. The public hostname has not been recorded in the repo.
