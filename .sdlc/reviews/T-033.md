### Root cause, checked against the QA numbers

These are reasoned from the CSS without rendering. QA re-measures.

- **1280: box 592 px at x=263 inside a 754 px form.** The 592 px was the input's intrinsic width, because nothing on the landing page set `width`. With `width: 100%` the input fills the 754 px form, which starts at x=263, so its centre is at about 640. The absolutely positioned `.go` (`right: 8px` in the `position: relative` `.ask`) now sits inside the box's right edge.
- **390: box 381 px, no gutters.** At 18 px the input's intrinsic width (about 381 px) was larger than the 358 px `.page` content box. Its min-content contribution pushed the `.landing` grid's auto track, and the `.launch` pane with it, past the page gutters. An input with a percentage width is a compressible replaced element, so its min-content contribution drops to 0. The pane then takes the 358 px track (16 px gutters from `.page { width: min(1240px, 100% - 32px) }`), and the box is 358 - 2*6 padding - 2*1 border = 344 px.
- **Vertical position (y 478 vs 428) and the large h1-to-help gap.** These came from the browser's default h1 (0.67em at display size) and p margins inside `.launch-head`. Zeroing them shortens the pane above the box by roughly 100 px. Because the pane is centred, the box moves up by about half of that, close to the mockup's 428.
- **Grey filled box.** The input now gets `background: var(--field)`, the `var(--line)` border and `var(--sh-in)`, the same tokens as the mockup's global `input[type=text]` rule, in both themes.
- **Scope.** `.ask` and `.launch` appear only in `landing.html` (checked with grep over the templates and `app.js`). The results form, `Search GPU` combobox and Clear are untouched. The global `:focus-visible` ring still applies, so the focus-box state is unaffected.
