### Spec issues

- **S-3 `src/vramsherpa/static/css/styles.css:568`: the loaded rows no longer fade in (rule 10).**
  - What is wrong:
    - `0f0052a` took `animation: whyIn var(--dur-2) var(--ease-out)` off `.why-list`. Its commit message says "nothing sets the mockup's `.is-loaded` hook".
    - The approved spec sheet (`docs/design/mockups/final-spec.html`, the motion table) says otherwise. For "Open How this is estimated" it lists: chevron rotates, skeleton shimmers, spinner turns, "then the five rows fade in", rows 220 ms, `cubic-bezier(.22,1,.36,1)`. Under reduced motion it is "rows appear at once".
    - The mockups and `docs/design/build/components.css:348` implement this with `.why-content.is-loaded .why-list { animation: whyIn … }`.
    - In the app, htmx inserts a new `.why-list` exactly once per card (`hx-trigger="click once"`). An animation on `.why-list` itself is therefore the app's version of that hook. The old rule did this job, and it was not a duplicate.
  - What it looks like (per-frame trace after the response lands, 390 px, 900 ms simulated latency):
    - Mockup: opacity 0, 0.31, 0.56, 0.73, 0.84, 0.90 …, with translateY moving from -6 px to 0 over 220 ms.
    - App: opacity 1 with no transform from the first frame. The rows pop in.
    - The open fade on `.why-content` only covers the first 220 ms after the click, while the loading state is still showing.
  - Fixed looks like:
    - Put `animation: whyIn var(--dur-2) var(--ease-out)` back on `.why-list`. The global reduced-motion block (`styles.css:644`) already turns it off.
    - Change `tests/test_ui_markup.py:1182-1185` to assert the animation is present on `.why-list`, alongside the `details[open] > .why-content` fade, instead of absent.
    - The wrapper removal and the box-sizing fix can stay as they are.
