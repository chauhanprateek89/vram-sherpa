### Nits

- **N-1** `src/vramsherpa/static/js/app.js:213-247`: N can differ from the chips for hand-written URLs. The script recounts on load from the checkboxes, but the server makes one chip per `family`/`quant_bucket` value, including duplicates and values with no checkbox. For example, `/results?vram_gb=24&context_tokens=4096&family=qwen&family=qwen&family=nosuch` renders `Filters (3)`, which the load-time recount turns into `Filters (1)`, next to 3 chips. The form cannot produce these URLs, so this is harmless. Fixed would be to skip the load-time recount (only recount on `input`/`change`/history), or to accept the gap with a comment.
- **N-2** `src/vramsherpa/static/js/app.js:249`: After an htmx history cache *hit*, the restored body has the server-rendered `checked` attributes, not the ticked state. So after Back, N (2) and the form disagree with the restored results (3 chips). N matches the checkboxes the user sees, so the count itself is right. The mismatch belongs to the htmx snapshot, which ADR-0008 left out of scope (re-wiring after a cache hit). This is noted for QA, and is not a T-012 change.
- **N-3** `tests/test_ui_markup.py` `test_filter_count_listener_is_delegated_on_document`: This is a source-text check, so it would still pass if the counting logic were wrong (for example, if it counted `-1`). The browser run above covers the behaviour. A small JS unit test is not available in this repo, so a QA browser step for "N updates in place" would close the gap.
- **N-4** `src/vramsherpa/static/css/styles.css:884`: `@keyframes whyIn` is defined here for the filters. When T-014 adds the breakdown's `details[open] > .why-content` animation, it should reuse this keyframe rather than define a second one.
