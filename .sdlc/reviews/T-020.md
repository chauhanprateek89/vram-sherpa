# Review: T-020 Focus ring, reduced motion and transparency, and removal of the old stylesheet rules

## 2026-10-27 (review 1)

**Commits reviewed:**

- `80c9954bd7d13e7f1dba0a78abda8c4c910caf60` T-020: Focus ring, reduced motion and transparency, and removal of the old stylesheet rules

**Verdict: pass**

### Summary

The commit rewrites `styles.css` into ADR-0001's six sections and deletes the legacy alias block. It also removes the pre-overhaul `label`, `input, select, button`, `.panel`, `.chip`, `.badge`, gauge and `.numbers-grid` rules, and the global `a:hover`. The many per-component focus rules are replaced by one 3 px `:focus-visible` ring. Reduced motion is gathered into a single block at the end. `ASSET_VERSION` moves to `20261027a`.

The commit touches four files: `main.py`, `styles.css`, `tests/test_styles.py` and `tests/test_how_it_works.py`. Only the last is outside the task's file list. It was a necessary follow-on: its CSS helpers had to read selector lists once the code rules were merged.

The result matches the approved design far better than the branch did before. With the pre-T-020 stylesheet on the same DOM, every approved state differed from its mockup by 40,000 to 390,000 px. With T-020 the differences are sub-pixel text in the form, plus two older defects listed below.

**Focus ring:**

- I pressed Tab up to 70 times on four pages: results (filters open, chips), empty, model detail and how-it-works. I did this at both widths and in both themes, and checked the Top Pick tile and the presets separately.
- Every focusable control shows `3px solid var(--focus)`: `#4A17B8` in light, `#CDB9FF` in dark. Offset is 2 px, except the quantisation buttons at 1 px.
- The radius is the component's own: 999 px for pills, 16 px for fields, 7 px for checkboxes, 12 px for the breakdown summary, 20 px for the Top Pick tile. A control with no radius gets 10 px: the brand, plain links and the filters and Top Picks summaries.
- These are the same values as the `.is-focus` elements in `final-focus-states`, control by control. The one exception is the gallery's unstyled `select`, which uses 10 px; the app's real select is 16 px, like the detail mockups.
- The presets draw the ring on the label (`:has()`). The Top Pick draws it on the tile, and the link's own ring is `none`.
- Screenshots: `rev020/focus/`.

**Reduced motion:**

- With `prefers-reduced-motion: reduce`, nothing on any page has a transition duration above 0 or an animation. I checked every element and `::before`/`::after`.
- The pages checked were results with a breakdown loaded, `.is-entering`, `.htmx-request` and the filters and Top Picks open, plus empty, unseeded, detail and how-it-works.
- The `.thumb` transition is 0 s.
- Without the preference, the same results page has 3168 moving elements, so the check has teeth.

**Reduced transparency:** I emulated `prefers-reduced-transparency: reduce` through CDP. Every `.pane` and `.lite` on all five pages, in both themes and at both widths, has a solid `--panel-solid` background, `backdrop-filter: none` and no rim (`::before` is `display: none`).

**No backdrop-filter:**

- I served the stylesheet with the `@supports not (...)` condition made true and every `backdrop-filter` declaration removed.
- Every pane is solid `--panel-solid`.
- The fallback comes after the 900 px `.lite` rule, so it wins at both widths.

### Nits (do not fail the review)

1. **`styles.css:627`.**
   - **What is wrong:** `.has-thumb .thumb { transition: none; }` inside the reduced-motion block is dead, because the `*` rule above it already sets `transition: none !important`. The `.sk-list i` reduced-motion rule also lives in a second block at `:505`, while `components.css` keeps both in one block.
   - **Fixed looks like:** delete the `.thumb` line, and move the `.sk-list i` line into the block at `:625`.
2. **`tests/test_styles.py:403`.**
   - **What is wrong:** the breakpoint normalisation special-cases `561`, so it only works for the one `max-width: 560px` query that exists today.
   - **Fixed looks like:** normalise `max-width: Npx` to N+1 for every value, then compare the set against `{900, 561}`. Alternatively, collect the raw widths and check that each min/max pair names the same boundary.
3. **`tests/test_styles.py:429`.**
   - **What is wrong:** `ASSET_VERSION > "20261025r"` would still pass if a later task reused `20261027a`.
   - **Fixed looks like:** nothing needed now. Each task's own test and the review's `git log -S` check cover rule 21.
4. **`tests/test_how_it_works.py:342`.**
   - **What is wrong:** `"a:hover {"` now matches `.top nav a:hover {`, so the second half of the assertion compares `.doc a` with the nav rule and proves nothing. This is review-T-019 nit 2 again.
   - **Fixed looks like:** drop the line. `test_pre_overhaul_rules_are_gone` already asserts that there is no global `a:hover` rule.
5. **The info-icon fix also changes the light glyph, from `#FFFFFF` to `#F7F6FF`.**

### Older differences from the mockups, not caused by T-020

I found these while checking every state. They are the same with the pre-T-020 stylesheet, so they do not count against this task. The orchestrator should route them before QA.

- **O-1, results-errors (both widths, both themes): the home form's VRAM field has no red border.**
  - **What is wrong:** the mockup marks `#vram_gb` with `aria-invalid="true"`. `components.css:82` styles `input[aria-invalid="true"] { border-color: var(--wont-fg); border-width: 2px; }`, and the `states.py` note says "the field gets a red border". In the app, `index.html:49-58` never sets `aria-invalid`, and `styles.css:547` styles only `.recompute input[aria-invalid]`. This is 1074 to 1644 px of difference, and the only visible mismatch left in an approved state. It dates from T-011/T-013.
  - **Fixed looks like:** set `aria-invalid="true"` on `#vram_gb` when `form_errors` names `vram_gb`, and widen the CSS rule to `.form-pane input[aria-invalid="true"]` or to the global form in `components.css`.
- **O-2, results-filters-open: the checkboxes drift by up to 2 px.**
  - **What is wrong:** the `.choice` labels are 0.4 to 1.2 px narrower than in the mockup, so the third checkbox in a row sits 2.0 px left at 1280 and 1.2 px at 390. The mockup's base rule `label, legend { letter-spacing: .01em }` (`components.css:77`) reaches `.choice` and `.seg label`; the app gives that letter spacing only to the field labels and legends. The same 0.15 px causes the sub-pixel anti-aliasing on the `2k`/`8k` presets in every form state. It dates from T-011/T-012.
  - **Fixed looks like:** add `letter-spacing: .01em` to `.choice` (`styles.css:354`) and `.seg label` (`:330`).
- **O-3, every form state: the end of the GPU placeholder anti-aliases differently.**
  - **What is wrong:** the app's `#gpu_search` has `list="gpu-options"`, so Chromium reserves room for its datalist indicator (the triangle shows on focus). The mockup's field has no `list`. The difference is a few pixels of the placeholder's last letters.
  - **Fixed looks like:** nothing here. It belongs to the ADR-0005/T-021 decision on the suggestion list.
- **Unseeded with the filters opened** (not an approved view, since the approved render has them closed): the app shows empty `Family` and `Quantization` legends, 90 px. The mockup omits them. This is noted only for QA.
